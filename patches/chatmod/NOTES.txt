osmw_chat — chat window QoL mod
===============================

Goal: font face/size control, no position snapping, text clearing, a
channel tab bar that splits System announcements out of the main chat pane,
and a client-level blocked-name list that hides a character's chat on this
PC (overlay included) without rewriting the real ring.

Status: MANAGED ABI 1 LIFECYCLE/CLAIMS HOST-VERIFIED (2026-09-05). Live
first-launch font timing and the full managed client matrix remain pending.

Managed delivery: a passive 32-bit feature DLL loaded first by osmw_core.dll.
Core owns configuration, logging, pristine-image resolution, the post-UiTick
callback and item-link send queue. The production client still runs the legacy
autoload set until the final atomic cutover; this build has not been deployed.

Runtime log: OFF unless asked for. [Debug] ModLogging in the game root's
config.ini, default 0, read once in dllmain.c's worker; with it clear no file
is opened and every mw_log() is a no-op. One key, shared with osmw_login.dll,
flipped from Maps++'s Tray -> Debug -> Client Mod Logging. Pruning kept the
count down but a player with nothing to debug still never asked for five files
per launch, every launch. Because the answer is taken at injection, a client
keeps whatever it started with for its whole life -- changing the key means
relaunching the clients, which is what the Maps++ notification says.

With it on: osmw_chat.<pid>.log in the game root, one per client, truncated at
each launch. One file PER PID, and a PID is never reused often enough to
overwrite, so the DLL prunes on startup and keeps only the five newest -- one
full Maps++ multi-client session, so a crash can still be read against the
other clients that were up at the time. A running client's log is never at
risk: it is held open without FILE_SHARE_DELETE, so the delete simply fails.
That same property is what makes the off path safe: it prunes to ZERO, so
switching logging off sweeps up what the troubleshooting session before it
wrote, without touching a live client's file.

A log stops at 1 MB with a final "size cap reached" line rather than rotating.
What matters in a mod log is the TOP -- signature resolution and the startup
block, which say whether the mod is working at all -- so rotation would discard
exactly the part worth keeping.

CAP*.BMP in the game root are the GAME's own screenshots, taken with the
client's screenshot key. They are the player's, not ours. Do not tidy them.

scan_offsets.py must report exactly one match for every required signature.
ChatMod_Append is optional (optional=1 in the game signatures.ini): zero
matches stands the overlay-drop down, not the rest of the mod. More than one
match still fails it -- do not hook the wrong site. More than one match on a
required pattern means it is no longer specific; zero means the client
changed. Do not widen a pattern to force a match without re-checking what it
now points at.


When the chat window is actually built
--------------------------------------
NOT on character login, despite appearances. The window is created during the
client's STARTUP INIT (in the same routine as "install weather" / "install
winfont" / "install system"), immediately hidden, and merely ShowWindow'd when
a character enters the world.

Consequences:
  - The two fonts exist from client start. Injecting into a running client is
    too late for the font hook -- use inject_test.py --launch, which is the
    same launch-then-inject sequence Maps++ will use.
  - A relog does NOT rebuild anything. That is why font.c carries a live
    re-apply path (below) rather than relying on the window being remade.
  - A suspended process has no module list, so LoadLibraryA cannot be resolved
    before the loader runs. --launch resumes first, then injects as soon as
    kernel32 appears (~5ms), which is still long before the client reaches its
    chat init.

The chat markup vocabulary, and what #L really is
--------------------------------------------------
The renderer dispatches on the character after '#' at 0x00477AB1: an index
table at 0x00477DA4 covering 0x23..0x65, a jump table at 0x00477D68, and a
second pair at 0x00477DE8 for 0x6B..0x79. Decoded, the engine implements:

    C c   24-bit hex colour, #cRRGGBB  (quantised to 565, see below)
    #     a literal '#'
    E e   used as a line break in the class/quest description text
    B b   K k   M m   N n   P p   R r   S s   U u   W w   Y y   G g

Those single letters, rendered and read off the screen rather than guessed
from the table:

    B b  blue      G g  green     Y y  yellow    P p  magenta   R r  red
    U u  UNDERLINE -- a real font attribute, not a colour
    W w  K k  M m  S s   all plain white, indistinguishable from no code at all
    N n  back to normal

So #K is not grey and #S is not small, however much they look like it. For a
dim stamp or label use #cRRGGBB; #c808080 is what the timestamp default uses.
Underline is the only non-colour style the markup offers.

Everything else in range -- including L and l -- lands on 0x00477D10, the
shared default case.

#L IS NOT A CHAT CODE. It is the line separator for the Affiche notice board:
0x00461370 counts occurrences of "#L" in a string and 0x004613A0 extracts the
Nth "#L"-separated segment. Those two helpers have exactly four callers,
0x0043582D / 0x0043588E / 0x00435CDF / 0x00435D3E, all inside the main-menu
panel that renders download\Affiche01.txt .. Affiche04.txt into a fixed box at
(140,120)-(420,440). There are ZERO calls from the chat module into that
region. The " Affiche" string near the guild strings at 0x0054FB08 is why
guild notices show as "[Leader Affiche]" -- that is the word used as a label,
not this mechanism.

So it is a live, in-use feature rather than a dormant precursor to anything.

WHAT THE INVESTIGATION DID TURN UP, verified by rendering it:

  - An unhandled "#" + letter is swallowed silently. "#L", "#l" and "#Q" all
    rendered as nothing at all, leaving text identical to the unmarked line.
    So there is an invisible side channel in chat text, using letters from the
    default set: A D F H I J L O Q T V X Z and their lowercase equivalents.
  - "#" + DIGIT is an emoticon, not a swallowed code. "#1#2#3#4" rendered as
    four smileys and "#7abc#9" as a smiley, "abc", a heart. Do not use digits
    in a payload.

Probe arbitrary markup any time with [Chat] ProbeText (semicolon separates
lines) and inject_test.py --probe. That is how all of the above was settled --
reading the dispatcher table alone got the digits wrong.


Timestamps, and why they are keyed on the real ring's slot index
----------------------------------------------------------------
A message record carries no time -- sender id, channel, sender name, text, and
nothing else -- so the time has to be observed as the message arrives.

The obvious place to stamp is where the mirror copies a record. That is wrong,
and wrong in a way that only shows up once you click a tab: the mirror is
REBUILT from the client's ring on every filter change, so a time taken at copy
time is the time you last switched tabs, on every visible line at once.

So the arrival time is recorded against the slot index in the CLIENT's ring,
which is stable for as long as the message lives, and looked up again on each
rebuild. mirror.c passes that index into the decoration; a synthetic record
(the probe) passes -1 and goes unstamped.

Times are observed for EVERY arrival, including messages the active tab filters
out -- they may be showing on another tab, and switching to it must not have to
invent a time. They are also observed when the feature is off, so switching it
on stamps what is already on screen instead of filling in gradually.

Messages already in the ring at injection have no observed time and are left
unstamped rather than given a made-up one. On the normal launch path this never
arises; injection happens during startup init, before any chat exists. It shows
up only when injecting into a running client, which is a development path.

WHERE THE STAMP IS WRITTEN: the line composer, not the record.

Every visible line is built by ONE sprintf, and every channel reaches it. The
call is at 0x0047A4FA (ChatMod_LineCompose + 25), calling the CRT sprintf at
0x004CD01E, with one of two formats:

    0x646B08  "#C00FFFF%s: #N%s"    name, text
              Local Party Guild Market World FD GM  (via 0x0047A489)
    0x646B00  "%s%s"                prefix, text
              System Info ch-99 (empty prefix) and PM ("You whisper to #Y%s#N: ")
              (via 0x0047A4E1)

The per-channel jump table at 0x0047A79C sends all ten channels, and the
default case for anything above 9, into one of those two -- so a single call
site covers the lot. mw_patch_direct_call repoints just that call; the CRT
sprintf itself is untouched, which matters because the whole client uses it.

In BOTH formats the LAST argument is the message text, pointing into our
mirrored ring, so the record -- and therefore its observed time -- is recovered
from the arguments alone, with no need to read the client's registers.
mw_mirror_real_slot maps our slot back to the client's, which is what the time
is keyed on.

The two obvious shortcuts are both wrong, and it is worth knowing why:

  - Prefixing the record's NAME field breaks click-to-PM. The hit test at
    0x00479F6A copies that field to build the whisper command, so the target
    would become a player called "12:43 Admin". Composing leaves the record
    pristine.
  - Prefixing at DRAW time (in the DrawLines loop, where the composed string is
    already sitting in the line buffer) overflows the right edge: the line was
    wrapped to a width measured without the stamp. Composing happens BEFORE the
    wrap is measured, so wrapping stays correct.

Composing also writes into the ~1KB line buffer rather than the record's 163
bytes, so a long message gets a stamp like any other.

mw_time_decorate, which prefixes the record's text and therefore lands after
the sender name, is kept as the fallback for when the composer hook cannot be
installed. It stands down whenever the hook is live.

Two things worth knowing about the format string:
  - #K IS NOT GREY. It is a handled code, so it looked like a reasonable
    choice, but rendered against the real renderer it is identical to plain
    white -- four characters of line budget for nothing. Use #cRRGGBB. The
    default is #c808080, picked by rendering 606060 / 808080 / A0A0A0 and
    comparing them on the real background.
  - A trailing space in the ini cannot survive: GetPrivateProfileString strips
    trailing whitespace. The separating space is appended in code instead.

It is not a printf format. The expander handles %H %M %S %% itself and copies
everything else through, because the string comes from config.ini and handing
user text to a %-formatter with a mismatched argument list is a way to crash
the client from an ini file.


Chat colours are RGB565, measured
---------------------------------
#cRRGGBB accepts 24 bits and keeps 16. The markup parser at 0x00477AB1 stores
the parsed colour into a WORD:

    00477B05   mov word ptr [esi+0xB4], ax      ; current colour
    0047774E   mov ax, word ptr [esi+0xB4]      ; copied into each text run
    00477762   mov word ptr [esi+0x7C], ax

Every access to both fields is word-sized, and the default colour global at
0x007E6940 is a word too, so the whole rich-text pipeline is 16-bit.

Measured with probe.c, feeding ramps of FF FB F7 F3 EF E7 DF per channel and
reading the rendered pixels back off a screenshot:

    red     -> F8 F8 F0 F0 E8 E0 D8      5 distinct    v & 0xF8   (5 bits)
    green   -> FC F8 F4 F0 EC E4 DC      7 distinct    v & 0xFC   (6 bits)
    blue    -> F8 F0 E8 E0 D8            5 distinct    v & 0xF8   (5 bits)

That is RGB565 by truncation, with no low-bit replication -- so the brightest
reachable colour from the hex path is F8FCF8, not FFFFFF. 65,536 colours, not
16.7 million.

PRACTICAL CONSEQUENCE: two colours differing by less than 8 in red or blue, or
less than 4 in green, are the same colour. Pick server palette values on that
grid (R and B multiples of 8, G multiples of 4) and what you write is what
renders. Nothing else is needed for colours to behave predictably.

Making it better would mean carrying more than 16 bits from parse to output,
and the only field that survives that trip is the 16-bit one. It cannot be
widened in place -- +0xB6/+0xB7 and +0x7E/+0x7F hold other attributes right
beside it -- so it would have to become a handle into a private 24-bit table,
on an engine the in-game overlay shares. Possible, but the gain over "use the
565 grid" is small and the blast radius is not.

Tooling for choosing colours that survive:

    palette.py check FF0000 FB0000     what they really render as, and which
                                       of them collapse into each other
    palette.py suggest 12              N colours on the 565 grid, spread by
                                       hue and legible on the pane background
    palette.py show <list>             write them to [Chat] ProbePalette and
                                       render them in a live client

    inject_test.py --probe             render the calibration ramps, or
                                       ProbePalette if one is set
    probe_read.py <pid> <row tops>     capture the pane and report the
                                       DISTINCT colours actually drawn

suggest walks the hue wheel rather than maximising a perceptual distance
metric. Those metrics weight green about 4x, and green is the one channel with
a spare bit here, so optimising against one hands you a palette of greens.


Chat cooldowns, and where the client keeps them
------------------------------------------------
The stock client answers a blocked message with "#R#S Please do not flood !#N"
(0x004F7298) and nothing else. It already knows the number it is withholding.

The gate is at 0x00409176, in the chat-send function that starts at 0x00409090:

    mov edx, [0x00701E48]   ; lastSend, ms
    add edx, eax            ; + this channel's cooldown
    mov eax, [0x00702980]   ; the client's ms clock, shared with much else
    cmp eax, edx
    jbe 0x004092BD          ; too soon -> the flood message
    mov [0x00701E48], eax   ; allowed -> remember when

eax arrives from a ten-entry jump table at 0x00409308, indexed by the current
channel in 0x00701E44 (read at 0x0040912F, restored afterwards at 0x004092D3 so
a one-off /w does not stick). Measured on this build:

    Local Party PM System Info FD    2s     Guild  3s
    Market GM                       30s     World  see below

World is the only conditional one, at 0x0040914B: 15s normally, but 10s when a
byte flag is set AND a counter reaches 50. On the live client it resolved to
10s, so both of those hold for that character -- the counter looks like level.

cooldown.c reads all of this out of the client rather than copying it: it walks
the table, and takes each constant from the `mov eax, imm32` the entry points
at. A shape it does not recognise falls back to the largest constant in the
block, which errs towards over-stating the wait rather than promising too soon.
A future build that rebalances a cooldown is therefore followed automatically.

The replacement is done by repointing ONE call: 0x004092CB, the client's own
"add a chat message" call for the flood case (mw_patch_direct_call again). The
detour recomputes the remaining time and substitutes the text. Nothing about
what is allowed changes -- the server enforces the cooldowns, and this only
reports a decision the client has already taken.

If the remaining time cannot be reconstructed the detour passes the client's
original message through untouched, so the worst case is the stock behaviour.


The three vanilla chat controls, and how the mirror broke them
--------------------------------------------------------------
The chat window ships with scroll up, scroll down and freeze. All three work
through the ring's view cursor, and all three stopped working when the window
began rendering from our private copy. This was OUR regression, not a missing
feature -- worth remembering before adding anything else that owns the ring.

  scroll        0x00462040, thiscall-less, takes a byte: 0x48 (VK_UP) walks the
                cursor back towards the tail, 0x50 (VK_DOWN) forwards towards
                the head, both clamped. Called only from the two button
                handlers, 0x004454F3 and 0x0044550A.
  freeze        0x00702858. EVERY append path reads it -- 0x00462188,
                0x00464B84, 0x0046594A, 0x00465A9F, 0x00465C64 -- and skips the
                "cursor = head" step while it is set. That is the whole
                mechanism: frozen means new messages stop dragging the view
                down. Toggled at 0x004454D4; the chat window also watches it at
                0x0047A062 and drops its cached line list when it changes.
  line count    0x004454A9 cycles the visible-line count 3..0x17. Untouched by
                any of this; it is the existing chatToggleSize.

All of them are OUTSIDE the span the mirror redirects ([HITTEST-0x200,
RENDER+0x800]), so they still move the real ring. Meanwhile publish_counters
was writing our own head into our cursor on every sync, which pinned the window
to the newest message and made all three look dead.

THE FIX: read the client's cursor and translate it, rather than inventing one.
translate_cursor maps the client's scroll position onto the nearest kept
message at or before it, using a real-slot -> mirror-slot map maintained
alongside the existing mirror-slot -> real-slot one. Freeze then needs no code
at all: when the client stops moving its cursor, ours stops with it.

Two details that matter:
  - The cursor is an EXCLUSIVE end. The render starts at cursor-1 and walks
    back, and the append path sets cursor = head, one past the newest.
  - publish_counters now runs on EVERY sync, not only when a message arrived.
    The scroll buttons move the cursor without adding anything, so the old
    "only publish when added" meant scrolling in a quiet channel did nothing.

MOUSE WHEEL (scroll.c) is layered on the same routine. The WndProc handles
none of 0x20A, and there are no ScrollWindow/SetScrollInfo imports, so the
window genuinely had no wheel support. Rather than move the cursor directly,
the handler CALLS 0x00462040 once per line -- so the wheel is exactly a button
press, clamping and all, and the in-game overlay scrolls with it because both
read the same cursor. Reimplementing the arithmetic would be a second copy to
keep true.

Three near-identical copies of that routine exist, one per scrollable buffer:
0x00462040 (chat), 0x00462E50 (0x00673D00, the parallel array) and 0x004633B0
(0x007430E8). A signature on the code shape alone matches all three, so
ChatMod_ScrollView pins the low half of the two globals to pick ours.

Windows sends WM_MOUSEWHEEL to the FOCUSED window, so the chat window has to
have focus. Scrolling whatever is under the pointer instead would mean the main
game window forwarding the message, and nothing subclasses that today.

Consequence worth knowing: on a heavily filtered tab one button press advances
the CLIENT's cursor by one real message, and most of those are not in the tab,
so the view moves only when the press lands on a kept message. Scrolling back
across a stretch with nothing kept correctly does not move at all. Verified on
the System tab: 37 kept of 827, and the mirror cursor stepped 37 -> 36 -> 34 ->
29 and then held, because there were no System messages further back.


Channels outside the named ten are real
---------------------------------------
Channel 99 turns up in normal play -- it is what the character info panel
(Gender / Race / Title / Name, from clicking a player) is routed through. Do
not use out-of-range channel numbers as sentinels; an earlier filtering
attempt picked 0x63 for exactly that and it collides.

The mirror keeps such messages only for a tab whose mask is every named
channel, so "All" shows them and a filtered tab does not. Otherwise "Trade"
would mean trade plus whatever else the client routes through this ring.


Finding your own character name
-------------------------------
It is not stored anywhere obvious. The client does put it in the main window
caption once you are in the world:

  MythWar osMW Patch ( ENGLISH version 1.0.48 - 3762 ) [ Behemoth: Borgmin ID 6911 ]

so mention.c reads it from between the last colon and " ID ". That is only
populated after login, so the lookup retries from the settings poll rather
than giving up at startup. [Chat] MyName overrides it.

Delivery: osmw_chat_launch.exe, a 32-bit launcher that starts main.exe with
the DLL injected before startup init. Being the same bitness as the client, it
resolves LoadLibraryA locally and uses that address as the remote thread start
routine, which works even though a suspended process has no module list yet.
The launcher is deliberately dumb: it always injects, and [Addons] ChatMod
decides whether the mod does anything. Maps++ drives this: its
ResolveLaunchExecutable prefers osmw_chat_launch.exe over main.exe, and
EnsureInjectPayload copies the DLLs out of Lib/ (and the launcher from next
to mapsplusplus.exe) into a game folder that lacks them. The launcher ships
at the release root rather than Lib/, because it looks for main.exe beside
itself and the Inno installer puts Maps++ in the game folder. GamePath stays
pointed at main.exe, which is what the overlay attaches to.


The line record, and how channel filtering works
------------------------------------------------
Record i lives at chatobj+0x80 + i*0x410:

  +0x000  text, 0x400 bytes, with the client's #C/#g/#y colour markup
  +0x400  Y offset into the chip atlas, or -1 for "no chip"
  +0x404  slot index into the global message array
  +0x408  line height in pixels
  +0x40C  chip Y offset within the line

The atlas is a vertical strip of 19px rows in channel order, so +0x400 is
channel * 19. Both routes to the channel agree; the filter uses the slot at
+0x404 instead, because that is what the client's own hit-test loop does and
it needs no assumption about the atlas pitch.

ONE RECORD IS ONE MESSAGE, not one visual line. A message that wraps just gets
a taller height -- measured live: 21px for a one-liner, 84 for a four-liner,
147 for a seven-liner, all with a valid chip and slot. There are no
continuation records, so there is no ordering problem to solve. Drawing is
bottom-up from index 0.

THE LINE LIST IS NOT THE DATA. Every render pass, ChatMod_Render walks the
message history backwards and rebuilds the list of visible lines into a local
stack buffer -- the 0x8230 frame the function opens with -- copying 0x410
bytes per line until the accumulated height fills the pane. The records at
chatobj+0x80 are the OUTPUT of that walk, not its input.

That is why filtering those records never worked properly. Whatever you do to
them, the next pass rebuilds them from history. Three attempts, all wrong:

  - Blanking records (zero height, chip -1, empty text) in the line-draw
    routine only. Filtered what was on screen, but every incoming message
    flashed: a second, incremental draw path in the same render drew it
    unfiltered for one pass.
  - The same blanking, moved to wrap the whole render. Killed most of the
    flash but not all of it, and switching filters never brought old messages
    back -- the pane only ever held what was already on screen.
  - Compacting the visible records to the front and lowering the line count.
    Cured the flash and caused a duplicating last line instead, because the
    incremental path keys on position between passes. It also crashed the
    client; see the note on +0x7A60 below.

THE MESSAGE STORE IS A RING BUFFER of 1024 slots at MsgArray, with three
counters immediately below it:

    base-0x10  write head, advanced on every append, wraps at 1024
    base-0x0C  tail, the oldest slot still held, advanced when the head laps it
    base-0x04  view cursor, the slot at the bottom of the displayed range
    base-0x08  visible line count (ChatMiniSize) -- a user preference, not
               part of the ring

Append is at 0x004620C0, __cdecl (channel, senderId, name, text) -- name THEN
text, not the other way around. It ends with a plain `ret` (caller cleans).
The flood path's add_message (channel, flags, name, text) is a different site;
it CALL rel32's this function (0x004092CB is one of 61 callers). Both network
chat and local echo reach it, which is why dropping here also hides the
in-game overlay.

Prologue, 7 bytes on an instruction boundary: `8B 4C 24 04 83 F9 05`
(`mov ecx,[esp+4]; cmp ecx,5`). The next instruction is `ja` -- do not
relocate it. Unique 12-byte pattern `8B 4C 24 04 83 F9 05 77 29 FF 24 8D`
does not collide with ScrollView at 0x00462040.

It already contains a per-channel mute for channels 0..5, keyed on flags at
0x6E03B0.. -- that is what the game's own channel buttons drive. It drops the
message at arrival, so it cannot separate System, but it confirms the model
name blocking copies: drop at append, do not punch holes in the ring.

The render walks backwards from the cursor towards the tail, formatting
messages into line records until the pane is full.

HOW FILTERING WORKS: A PRIVATE RING. The chat window's own code refers to the
ring through exactly twelve absolute addresses -- all plain [reg+disp32] or
[disp32] operands, spanning the render and the hit-test. mirror.c allocates a
private ring in the same layout and rewrites those twelve disp32s to point at
it. The window then renders entirely from our copy, natively, so channel
chips, #C colour markup, #1 emoticons, wrapping and scrolling all remain the
client's own code; every other subsystem keeps reading the untouched original.

The mirror is built APPEND-ONLY, exactly like the ring it shadows, so a
message keeps its slot index for as long as it lives and the window's cached
line list stays valid. Changing the filter renumbers everything, so that path
rebuilds the ring and invalidates the cached line list together.

Do not go looking for a cheaper filter. Three were tried and all failed for
reasons rooted in the model above:

  - Blanking the line records the walk produces. They are output, not input;
    the next pass rebuilds them. Incoming messages flashed and switching
    filters never brought old messages back.
  - Compacting those records and lowering the line count. Duplicated the
    newest line, because the incremental draw path keys on position between
    passes -- and it CRASHED THE CLIENT, because the "line count at +0x7A63"
    is the high byte of a packed dword whose low 24 bits are two 12-bit
    indices into the list. Lowering the count left them past the end.
  - Parking unwanted channels above the valid range, on the theory that the
    walk drops them. It does not: 0x0047A476 branches to 0x0047A6C6, which is
    `mov byte ptr [esp+0x13], 0` -- "this line has no chip" -- and then falls
    straight back into the formatter. The message draws normally, just without
    its coloured pill. That is exactly what it looked like in game.

+0x7A60 IS A PACKED DWORD, NOT A SELECTION. High byte = the line count, with
bit 7 set; low 24 bits = two 12-bit indices into the line list. The "line
count at +0x7A63" is that high byte. Writing the count on its own -- which the
compacting version did, lowering it to the visible total -- leaves those two
indices pointing past the end of the list. That is the most likely cause of
the client crash seen during development. Do not write it.


Live font re-apply, and the wrapping limit it exposed
------------------------------------------------------
Changing a font setting now takes effect without a restart. font.c keeps the
parameters the client originally asked CreateFontA for, rebuilds from THAT
baseline plus the current settings, selects the results into the two device
contexts, stores the text font back at chatobj+0x7A80, re-runs the chip atlas
builder (which is re-callable -- it makes and destroys its own brushes) and
drops the cached line list.

Two details worth keeping:

  - The baseline is taken from the CreateFontA shims when the mod was loaded
    at launch, and otherwise from whatever is selected in the DCs when we
    attach. That second path is why font settings work on a client we injected
    into late. It anchors wrong only if you eject and re-inject a client that
    was launched WITH the mod -- the DCs then hold the previous instance's
    overrides. Relaunch for a true baseline.
  - The poll runs from BOTH the window procedure and the render. The window
    procedure alone was not enough: an idle or hidden chat window receives
    almost no messages, so an edit only applied when you happened to click on
    it. Both callers share one throttle.

LINE WRAPPING DOES NOT TRACK THE FONT. This is a pre-existing client
limitation, not something the mod introduced -- it was simply never visible
until large sizes were tried. Changing the face is safe. Changing the SIZE by
a little is safe (18 against the client's own 16 wraps correctly). Changing it
a lot overflows the right-hand edge: at 24 whole words are cut off.

Ruled out by measurement, so do not re-test these:
  - Proportional vs monospace. Consolas 24 overflows exactly like Verdana 24.
  - The declared cell width. FontWidth=12 with a 24px font changed nothing.
  - Stale cached layout. A line injected AFTER the change overflows too, and
    the view is invalidated on every re-apply.
  - A separate measuring DC. The engine measures through 0x007DED10+0x90,
    which reads back as the SAME handle as chatobj+0x44, so the font swap
    already covers measuring.

THE WORKAROUND, and it is a good one. The wrap assumes 8 pixels per character
because that is the cWidth the client's own text font is created with. Pin
FontWidth to 8 and raise FontSize freely: GDI condenses every glyph into the
8px cell, so the text gets taller without getting wider and the arithmetic
stays true. Verified in game at Consolas 22 and again under a stress line of
"WWWW MMMM" repeated across the pane -- no clipping, clear margin.

A SECOND, HARDER CEILING: 18 PIXELS. Above it the client cuts the bottom rows
of every line.

TEST IT WITH UNDERSCORES, NOT DESCENDERS. An underscore sits lower than a y or
g tail, so it goes first. At 19 the tails still look about right -- roughly
nine tenths present -- while every underscore has already vanished. Bisecting
on descenders alone gives 19 and is wrong; bisecting on underscores gives 18,
which is correct. This mistake was made and corrected here.

  18   underscores and tails both drawn in full
  19   underscores gone, tails ~90%
  20+  tails visibly cut as well

It is NOT the descent. Consolas 18 and Consolas 20 both have a 4px descent and
only 20 clips, so it behaves like a fixed pixel budget rather than anything
derived from the font. The stored line height is not the cause either -- it
measures 25px for a 22px font, comfortably more than the glyphs need. The clip
is somewhere in the engine's draw path (0x00471AF0), a large SEH-wrapped
function that has NOT been traced. The ceiling is empirical.

Consequences:
  - No font setting avoids it. FontWidth does not help; it is vertical.
  - 18 is the hard ceiling for FontSize, and the presets stop there. That is
    +2px over stock, which is all this client will give.
  - FontWidth pinning is therefore no longer needed by any preset: Consolas
    and Cascadia Mono both wrap correctly at 18 unpinned. It stays available
    for anyone choosing a wider face.

The flicker on clicking a tab is the same defect seen twice: the click
invalidates the line list, the first pass re-measures and draws at the true
height, then the cached path draws clipped. At 18 nothing clips, so there is
nothing to flash.

So there are two safe routes for WIDTH, and fontpresets.py measures both:

  natural  a height at which the face already renders real text at <= 8px per
           character. Proportions untouched. Consolas 18, Cascadia Mono 19,
           Courier New 17.
  pinned   FontWidth=8 at any height. Slightly condensed, but unrestricted.

MEASURE WITH A SENTENCE, NOT tmAveCharWidth. GDI's average is roughly the
width of 'x' and badly understates a proportional face: Tahoma 22 passes on
tmAveCharWidth and still clips in game. fontpresets.py measures a real sample
string through GetTextExtentPoint32 instead, and its numbers match every
in-game result we have (Consolas 18 fine, Verdana 20 clipped, Tahoma 22
clipped).

Prefer fixed-pitch regardless. With a proportional face the 8px budget is an
average, so a line of wide capitals can overflow even below the reported
natural height.

Still untried, if a fully unrestricted natural size is ever wanted: narrow the
client rect during the render in proportion to the measured glyph-width ratio,
the same mechanism the tab strip uses vertically.


Chip scaling (chips.c)
----------------------
Chips grow with the message font. HEIGHT ONLY -- width stays 38 on purpose.

Each channel's atlas offset is already data (the builder writes chatobj+0x58 +
channel*4), so the pitch needs no code patch at all. Only three blit heights
do, all `push imm8`, anchored to signature-resolved functions and verified
before patching:

  MW_RENDER    + 0x367     push 0x12
  MW_RENDER    + 0x58D     push 0x12
  MW_DRAWLINES + 0x062     push 0x12

Width was left alone deliberately. Changing it would also mean moving the text
origin, hardcoded at nine further sites (0x28 at 0x00479874 0x00479899
0x0047A11A 0x0047A185 0x0047A199 0x0047A280 0x0047A85C 0x0047AA02 0x0047AA24)
plus six width sites (0x26 at 0x00479D05 0x0047A150 0x0047A40B 0x0047A631
0x0047A7EF 0x0047A836) -- fifteen more immediates that all have to agree, for
a gain nobody would notice. 0x19 at 0x0047A159 / 0x0047A7FC is the bottom pad,
not chip related.

The chips are STRETCHED FROM THE CLIENT'S OWN, not redrawn. chips.c hooks the
atlas builder, lets it draw normally, snapshots the result, then StretchBlts
each 38x18 cell into a taller one and republishes the offsets. That keeps the
client's colours and labels, so it stays correct on any locale -- redrawing
would have meant hardcoding ten colours and ten English labels.

Measured on a live client: 18px cells at the stock font, 24px at FontSize 22,
and a clean revert back to 18. Judge it with chipmeasure.py rather than by
eye; a screenshot of an 18px chip beside small text reads as "too tall" and it
is not.


FontWidth is for the MESSAGE font only
---------------------------------------
It exists to hold message text inside the 8px cell the wrap arithmetic
assumes. The chips do not share that concern -- they are drawn once into a
fixed 38px atlas cell -- and applying it to them forced their cell from 6 to 8
and clipped every label to "Marke", "Syste", "Worl". Use ChipFontWidth if a
chip cell really needs overriding.

font.c now also narrows the chip font automatically when the widest label
would not fit the 38px chip, and logs when it does. A condensed label beats a
truncated one, and it self-corrects whatever face is chosen.


The tab strip: reserving space, and drawing into it
---------------------------------------------------
The render anchors chat text at (top + bottom - 25) and fills upwards until it
has used (bottom - 25) pixels, both read from the client rect at chatobj+0x28.
Adding S to `top` and subtracting S from `bottom` for the duration of a pass
leaves the anchor exactly where it was while shortening the fill by S, which
frees S pixels at the TOP with the text still hugging the bottom.

S must stay under 25. The render's background blit covers (0,0) to
(width, bottom - S) and the lowest line sits at (bottom - 25), so at S >= 25
the newest line would draw onto stale pixels.

Two things cost a build each and are not obvious:

  - DRAW THE STRIP AT THE PRESENT, NOT AFTER THE RENDER. The render presents
    (offscreen surface -> window) near its own end, at ChatMod_Present, and
    the next pass opens by blitting the background over the whole surface.
    Anything drawn after the render returns is wiped before it is ever shown.
    Hook ChatMod_Present and draw there. That helper is shared with the PHIZ
    window, so check the object before decorating.
  - THE PRESENT IS CALLED FROM INSIDE THE RENDER, while the rect is still
    shifted, and it takes its blit destination and size straight from that
    rect. Put the true rect back for the duration of the copy or the whole
    surface lands 20px down the window.

And one self-inflicted trap: geometry.c's cache refresh calls GetClientRect,
and the reposition it hangs off runs INSIDE the render -- so it silently threw
the reservation away and the strip blitted off the top of the window. Anything
that re-reads that rect must re-apply mw_tabs_rect_shift().


Clearing: the line store is a view, not the data
------------------------------------------------
chatobj+0x484 (stride 0x410, count at +0x7A63) looks like the chat window's
line store, and the client's own show routine does zero it. It is a VIEW: each
record holds a slot index into the global message array at MsgArray, and the
window rebuilds it from that array every render pass. Zeroing it changes
nothing -- measured, the records were byte-identical again 1.5s later.

Clear the source instead, by calling the client's own buffer reset
(ChatMod_ResetBuffers, what runs on entering the world). Two things to know:

  - It also resets the visible-line count at MsgArray-0x08 to 7. That is
    ChatMiniSize, the value the Maps++ chatToggleSize hotkey cycles, so save
    and restore it around the call.
  - It clears the message source, so the in-game overlay empties as well as
    the chat window. That is inherent, not a bug.

And nothing is visible until the full-redraw flag (ChatMod_DirtyFlag) is set
to 1. The render consumes it and zeroes it at the end of each pass, so reading
it back as 0 afterwards is correct. Without setting it the offscreen surface
keeps the pixels it already had and the clear appears to do nothing -- which
is exactly how this first shipped, and how it was caught.


Unloading: never park a thread inside the DLL
----------------------------------------------
FreeLibrary unmaps the code immediately. A thread sleeping inside this DLL
wakes up in freed memory and takes the whole client down with it -- that is
exactly what happened the first time the settings poll was a background loop.

Two rules follow, and both are load-bearing:

  - The worker thread RETURNS once it has installed everything. Anything
    periodic runs from the WndProc, on the game's own thread.
  - --eject calls the exported osmw_prepare_unload remotely first, which stops
    and joins the worker, and only then calls FreeLibrary. Do not remove that
    handshake, and do not add an export-free eject path.
  [ ] 3  remove position snapping, unlock resize, persist geometry
  [ ] 4  text clearing
  [ ] 5  channel tab bar (All / Chat / System)

----------------------------------------------

clean quit, not a crash; error.txt ending at "menu begin loop" is not a crash

  [ ] Chat window appears and behaves normally
  [ ] Alt-tab away and back: process stays alive
  [ ] Maps++ still attaches and its overlay still aligns
  [ ] Eject leaves the client running and usable

  [ ] Font looks right in game; chips still line up with their messages
  [ ] Chat window stays where you drag it, and can be resized

The Maps++ settings page
------------------------
SUPERSEDED, and now DELETED. ui/chat/ was a standalone page (index.html +
main.js + style.css) speaking the host contract below. The settings are a tab
in the Maps++ Settings window, built by addons/chat_mod.ahk from field
descriptors that both of Maps++'s frontends render. That removed the bespoke
page, its message router and a hand-built native fallback, and made the tab
match every other settings pane for free.

The directory itself was removed once it had sat there long enough to become a
liability: it still shipped in every release (build.ps1 copies ui/ wholesale),
and it held a third copy of the font preset table that had already drifted out
of step with the other two. The presets now live in exactly two places --
patches/chatmod/tools/fontpresets.py, which is the source of truth because it
measures against the real renderer, and _CHATMOD_FONT_PRESETS in
addons/chat_mod.ahk, which mirrors it.

ui/chat_tabs/ is a NEW standalone page and is not the same thing. It is the
channel-tab editor, opened from a button on the settings tab, and it exists
because tabs are the one chat-mod setting that is a language rather than a
value. Its contract:

  host -> page   { type: 'init-tabs', rows, channels, layouts,
                   maxTabs, nameMax, notice }
                 { type: 'set-rows',     rows }
                 { type: 'tabs-preview', spec, length, max, error }
  page -> host   { type: 'init-request' }
                 { type: 'preview', rows }   { type: 'layout', index }
                 { type: 'accept',  rows }   { type: 'cancel' }

A row is { name, channels: [bool x 10] }. The page never builds or measures a
tab spec: it sends rows and is told what they came to. Parsing, formatting and
validation are all in addons/chat_mod.ahk, in one copy, and the preview the
page shows is produced by the same functions the OK button runs -- so it cannot
promise a result the save would not produce. The AHK parser is a deliberate
port of parse_tabs() below, for the same reason.

The keys are unchanged, and are still exactly the [Chat] names in config.ini.
The contract is kept here because it is what any future standalone page would
have to speak:

  host -> page   { type: 'chat-settings',       settings: { ...ini keys... } }
  page -> host   { type: 'chat-settings-request' }
                 { type: 'chat-settings-save',  settings: { ...ini keys... } }
                 { type: 'close' }

Keys are exactly the [Chat] names in config.ini, so the host writes them
straight through with no translation table. Nothing needs to be told to the
game: the DLL's own settings poll picks the file up within about two seconds.

The font presets are duplicated in _CHATMOD_FONT_PRESETS (addons/chat_mod.ahk)
and in fontpresets.py. Keep them in step; the tool is the source of truth
because it measures.


Client-level name blocking
--------------------------
The game's ignore, if it is used at all, is per logged-in character. This list
is per PC / shared game-folder config.ini, matching on sender name (record
+0x08, 20 chars + NUL, case-insensitive exact). Empty names never match. Your
own name (mw_mention_name()) cannot be added. System (6) and Info (7) are
never dropped, even if the name matches. Cap 32 names, no commas inside a
name. Storage: [Chat] BlockedNames=Alice,Bob. Dedicated ~1024-byte reader
(mw_cfg_copy), not the 256-byte mw_cfg_str ring. Maps++ writes that one key
from Edit blocked names and from nowhere else -- it is not in _CHATMOD_SPEC,
so Settings Save cannot clobber a Ctrl+click. Reset to Defaults does not
clear it. Empty list writes an empty value, never IniDelete.

Two gates, on purpose:

  1. Append detour (optional ChatMod_Append). If the name is on the list,
     return without calling the original, so the message never enters the
     REAL ring. Overlay, history, every other reader never see it. Same
     model as the client's channel mute. If the signature misses or the
     7-byte prologue cannot be hooked, this feature's overlay drop stands
     down and the rest of the chat mod stays up. keep_message still hides
     leftovers in the chat window from the name list alone.

     JMP to a C function then CALL the trampoline corrupts the stack: the
     original is cdecl and expects the original frame. append_gate is
     __declspec(naked) and JMPs the trampoline or RETs.

  2. keep_message skips blocked names when the chat window rebuilds. That
     is leftovers already in the ring: they vanish from the window within
     a settings poll. We do NOT compact or punch holes in the real ring.
     Overlay leftovers age out with the 1024-slot history. Compacting the
     visible store crashed the client during tab work (see +0x7A60 above);
     rewriting the real ring would hit every other reader besides.

Ctrl+left-click adds; it never unblocks. HitTest (0x00479EC0, thiscall,
two pointer args, ret 8) already has the name in hand at +0xAA:
`lea esi, [eax+MsgArray+8]` (eax = slot * 0xC0). The client has already
skipped System/Info/ch99/self before that site. Diverting there swallows
the whisper without reimplementing wrap geometry. One caller, 0x0047A227.

HitTest is one of the twelve ring references the mirror rewrites, so after
mw_mirror_install that LEA points at OUR copy. The hook reads the name
from mw_mirror_base(), not the real MsgArray -- the slot index is in the
mirror. The site check is the 6-byte LEA whose disp32 equals that base+8.
Prologue of HitTest pushes ebx, ebp, esi, edi and never allocates stack
before +0xAA, so swallowing is `pop edi; pop esi; pop ebp; pop ebx; ret 8`
-- the same epilogue as the early-outs already in the function. Same
naked-gate rule as append: JMP the trampoline, do not CALL it.

Already on the list / own name / empty: swallow, no confirmation. List
full: swallow and inject "Block list is full." Success: copy the name
off the ring, then rebuild, then mw_mirror_inject on Info (channel 7)
with name "Chat mod" and text "Blocked Alice." Info so the chip is not
Local (and keep_message never drops it). The name must be copied first:
confirming from the ring pointer after rebuild printed "Blocked ." with
a hole where the name had been. Inject-then-rebuild would wipe the line.
It is still ephemeral (gone on the next tab switch), which is the
existing inject contract.

Trial log (with [Debug] ModLogging on): look for `block:` lines -- names
loaded, append hooked / missing, whisper site matched or refused, added
"Name" (n/32). A missing Append signature logs overlay drop disabled and
leaves fonts/tabs/everything else up.



Chat item links (links.c) -- the composing half
------------------------------------------------
ALT+click an inventory item and its compose token goes into the chat input.
The server does the rest: it resolves the token against that player's own
inventory, snapshots the item, and broadcasts the name wrapped in markers the
stock renderer swallows. So an unmodded client reads the line as ordinary
text. Wire contract: mw-tools tools/client-dll/item-links.md.

THE CHAT INPUT IS NOT A WIN32 EDIT, and it is not the login widget either.
It is a static instance of the client's own edit-box class:

    0x0065fbb0  instance      (ctor 0x409060, run by the CRT init at 0x4ce070)
    0x004f71e8  vtable        -- its +0xa0 is 0x409090, the chat send routine,
                                 which is what identifies the instance
    0x0047bcc0  AppendString  vtable+0x68  __thiscall(const char*), ret 4
    0x0047bda0  Clear         vtable+0x70  __thiscall(), no args
    0x0047bfa0  GetLength     __thiscall(), no args
    [inst+0x120] text cap, 0xa0 (160) for this box, -1 would be unlimited
    [inst+0xcc]  glyph cells, 16 bytes each -- never memcpy a string here

The client does this to itself at 0x433dce (the quick-chat panel that puts
"Heal me please!" in the box): Clear then AppendString. ChatInputInstance is
anchored on that site, so the signature both finds the instance and pins the
call pair being copied. We use AppendString WITHOUT Clear, so the token lands
at the caret and what the player already typed survives.

DO NOT use vtable+0x18 (0x47ae20), which is what login drives. It is the KEY
handler: it gates on the box being enabled and focused, routes 0x08..0x1b
through a special-key table, and drops the character outright while Ctrl is
held (GetKeyState(VK_CONTROL) at 0x47ae5b). AppendString bypasses all of it.

THE CAP IS ENFORCED PER CHARACTER. Once full, the raw insert resets its
pending byte, inserts nothing and returns 0x80004005. AppendString does not
check up front, so appending to a nearly-full box inserts a PREFIX of the
token -- and half a token is not a token: it passes the server's sanitiser
and gets broadcast as literal text. insert_token checks GetLength first and
refuses as a whole.

WHERE THE CLICK IS CAUGHT. The inventory is in the MAIN game window, which
nothing subclasses, so this is the one feature here that does not go through
the chat window's message handler.

The callback dispatches TWICE: on the UI event byte, then on ebx, which says
which control was hit. The 24 inventory slots are ebx 0x64..0x7b, one control
each, and that case is:

    0042862f  cmp [0x743820], ebp        ; 0 = inventory mode, else pets
    00428635  lea eax, [ebx - 0x64]      ; slot = control - 0x64, so 0..23
    00428638  mov [0x6aa6e4], eax        ; the client publishes the slot here
    00428647  cmp eax, 0x18              ; range-checked for us
    00428650  lea edx, [eax + eax*4]     ; edx = slot * 5
    00428653  cmp [edx*4 + 0x6aa748], ebp ; HOOKED, 7 bytes; edx*4 = slot*20
    0042865a  jl  0x4288ab               ; empty slot: client does nothing
    0042866d  call 0x409690              ; the pick-up we pre-empt

The grid base and the abort address are read out of the hooked bytes (the
cmp's disp32, and where the following jl goes) rather than given signatures of
their own, so they cannot drift from the site.

GETTING THIS WRONG COST A TEST CYCLE, so: the first version hooked 0x4284a4,
which also compares a slot against the same grid array and which the RE notes
describe as "the inventory click handler". It is not. It is in the ebx==1
case, a single button whose other branch walks pet records at stride 0x74, and
an inventory click never goes near it. Every signature resolved, the hook
installed, the log looked perfect, and nothing happened. Resolving the ebx
jump table (index 0x428a3c, targets 0x428a20) is what identifies the grid
block; "it compares against 0x6aa748" is not enough, several blocks do.

Eating the click matters: left alone the client's next move is the 0x409690
call that lifts the item onto the cursor, which is not what ALT+click should
do. The jl target is the client's own "empty slot, nothing to do" path -- same
frame, same stack -- so it is exactly the no-op the click should have been.
Same trick as the Ctrl+click swallow above.

NO EDGE DETECTION IS NEEDED, and that is checked rather than assumed. Window
callbacks run every frame, so a naive hook would fire continuously while the
button is held. This one cannot: the callback opens with a switch on the UI
event byte at 0x42821b (index table 0x428914, jump table 0x428904), and
resolving both shows only 0xF5 (WM_LBUTTONDOWN) enters the block the hook sits
in. 0xF2 -- the synthesised "still down" event that arrives every frame -- goes
to a different handler, and 0xF4 mousemove goes straight to the do-nothing
path. Once per press, on the press.

Setting: [Chat] ItemLinks, polled with the rest, so it takes effect within a
settings poll rather than at next launch.

CLICKING is built too. A click in the pane maps to a line record (0x410 bytes
at chatobj+0x80, drawn bottom-up from index 0, one per message however many
rows it wraps to) by walking up from the pane bottom accumulating +0x408
heights. The record's text at +0x000 is the COMPOSED line, and composition
happens before markup is stripped, so the markers are still there to decode.

Whole message, not a sub-span: a click anywhere on a line carrying a link
opens it. Measuring x would mean reproducing the client's wrap, and the
client's own HitTest is no help -- it fires on the sender NAME for click-to-PM,
not on the body. A line with no link falls through untouched, so click-to-PM
still works.

The request is ItemInfo (0x7000d) kind 200 with the link id in the slot field,
built and sent directly through SendPacket 0x454060 rather than the client's
request builder (which exists to add the inventory page offset). The reply is
caught at 0x4567be, where esi points at the incoming text just before the
client copies it to its tooltip buffer. NOT consumed: the stock copy is
harmless because the tooltip only draws while a game panel hovers a slot, and
the click happened over the chat window. The "#O#J" sentinel is what
distinguishes a link reply from a hover reply, so the two cannot race.

THE PANEL is the CLIENT'S OWN tooltip renderer, 0x44c760, __cdecl(int zero,
void *record). A linked item therefore looks exactly like the same item
hovered in the inventory -- no GDI, no markup parser, no palette to keep in
step. The first version hand-drew a GDI panel in the chat pane and was thrown
away: matching the game's look by hand is a losing game, and it also put the
panel in the wrong window.

The renderer positions itself from the mouse globals, clamped to 800x600:

    0044c7c2  mov ecx, [mouseY]      ; renderer + 0x64
    0044c7c8  mov eax, [mouseX]      ; renderer + 0x69
    0044c7cd  ...  x = mouseX - 0x64 ; y = mouseY - height - 0x10

Both globals are read out of the renderer at those fixed offsets, so they
cannot drift from the function consuming them. Positioning is just parking the
mouse position for the call and putting it straight back; nothing observes it
in between because it all happens inside one frame's draw.

Horizontally that means centred (400 - 0x64, against a fixed 0xc8 width).
Vertically the box is pinned near the TOP, and the height drops out of the
arithmetic entirely:

    0044c7cf  sub esi, ebp        ; y = mouseY - height
    0044c7d4  sub esi, 0x10       ;   - 0x10
    0044c7df  jge 0x44c7e4
    0044c7e1  lea esi, [ecx+0x20] ; NEGATIVE -> y = mouseY + 0x20

An anchor low enough to drive that subtraction negative lands the box at
anchor + 0x20 flat. Height is floored at 0x50 (0044c7b8), so any anchor below
0x50 + 0x10 = 96 always takes that branch. That is what stops a long tooltip
running off the bottom -- it grows downwards from a fixed top rather than
upwards from a fixed bottom, so the height nobody outside the renderer knows
stops mattering.

The `record` argument is the same 20-byte item record the shop list ships
(ShopPackets.npcVendor): int32 id at +0, uint16 SPRITE at +8, stack count byte
at +0x10. Only the sprite matters here:

    0044c774  cmp word ptr [eax+8], bx      ; validity, signed
    0044c849  movsx ecx, word ptr [eax+8]
    0044c854  mov edx, [ecx*4 + 0x817000]   ; the sprite table

There is no "draw no icon" value -- a negative sprite fails that first test and
the renderer returns having drawn nothing at all. So a zeroed record draws
sprite 0 for EVERY item, which is what the first build did. The server now
sends item.file encoded onto the front of the reply, after the sentinel, as the
same swallowed `#x` digits a link id uses (so an older mod build renders
nothing extra rather than stray characters).

The count byte at +0x10 is only read when the first argument is non-zero, and
we pass zero, so it can be left alone.

DISMISSING IT: right-click (like every other window in this client) and
Escape (which opens the logoff menu, so the panel must not sit on top of it),
both polled with GetKeyState from the same per-frame thunk that draws it. A
left click in the chat pane dismisses it too, but that alone is useless once an
active channel has scrolled the link out of the pane.

And LEAVING THE WORLD dismisses it, which is not a key at all. Drawing from the
screen present means drawing on every screen the client has, so a panel left
open at logout came back over the server-select list. The gate is the client's
game state at 0x74313c (ChatMod_GameState, the same global Maps++ reads):
below 5 the client is loading or at login. An unresolved signature reads as
"in world", so a missed scan costs the gate, not the feature.

WHERE IT DRAWS, and the site that looked right and was not. The draw context
0x7e6a04 is null outside a render, so this cannot be drawn when the reply
arrives; it has to be called from the frame.

The obvious site is the window manager's draw pass 0x45e7b0(list), which walks
its list calling [node+0x20] and falls out at 0x45e8ee. That is genuinely
"after every window has drawn" -- but the pass opens with

    0045e7c6  mov eax, [esi]      ; list head
    0045e7c8  cmp eax, esi
    0045e7cf  je  0x45e95b        ; EMPTY LIST -> straight to the exit

so with no panel open it never reaches 0x45e8ee at all. The chat window is a
real Win32 window, not a manager node, so in ordinary play both lists (0x629374
and 0x6293a0) are empty and a hook there simply never runs. The symptom said
exactly that and was still easy to misread: the log reported the panel shown
and nothing appeared, until F9 opened the timer panel and the tooltip appeared
alongside it. One window in the list was all it took.

The site that always runs is the screen present -- an indirect call through a
function pointer at 0x7e69f4 that every one of the client's ~60 frame loops
ends with:

    push [0x7e6a04]   ; the draw context
    call [0x7e69f4]
    add  esp, 4

So links.c hooks no code for this at all: it swaps that pointer for a __cdecl
thunk that draws and chains. One slot covers every loop the client has, and
the context is by definition valid, since it is the argument. The only writer
is the display-mode setter 0x4a0bb0, which picks between 0x4a0bf0 and 0x4a0d20;
mw_links_poll re-asserts the swap in case it ever runs again.

The general lesson, which is the same one the ALT+click hook already taught:
a site being on the right code path is not the same as it being reached. Check
the early exits before concluding a silent hook is a wrong address.

The text goes into the client's tooltip buffer only for the duration of the
call and is restored after, so hovering an item while the panel is open still
shows that item.

Watch out for OBJ_FONT: wingdi.h already defines it. Do not reuse the name.

REPEAT CLICKS: the mod keeps the last 4 replies for 60 seconds and serves a
re-opened link from that instead of asking again. Re-opening is the ordinary
way the feature gets used -- open, read, close, check it again -- and it is
also the shape of the obvious abuse. Caching is safe because the server froze
the item at link time and rendered the reply for THIS viewer, so nothing in it
belongs to anyone else; what drifts is the market-price line and the reader's
own level colouring, hence the expiry. An entry already in the cache is
refreshed in place rather than appended, so hammering one link cannot evict the
other three. Empty slots hold id -1, because link id 0 is real.

None of that is a security control -- a modified client ignores every line of
it. The server rate-limits the request separately
(ActionType.ChatLinkInspect).

Deferred, with reasons
----------------------

    straight to the main game window (its WndProc PostMessages 0x100..0x108
    onward), so the text the player types is never visible to us here.
    Implementing it means hooking the client's chat-send path, which is a
    bigger change than the rest of Phase 4 combined. The hotkey and the
    posted message cover the same need. Typed "/block" is the same trap.
  - Tracing the 18px vertical clip to its cause. It is somewhere in the text
    engine's draw path at 0x00471AF0, a large SEH-wrapped function that has
    NOT been disassembled. The ceiling is empirical, not understood. Ruled
    out: the font descent (Consolas 18 and 20 both have descent 4 and only 20
    clips), the stored line height, chip scaling, and a separate measuring DC.
    Worth doing only if someone wants a chat font above 18.


Window placement
----------------
Once FreePosition is on, placement is a ONE-SHOT decision taken on the first
reposition pass and never revisited:

    saved geometry?  -> put it back where the player left it
    nothing saved?   -> call the original, which docks it beside the client

Everything after that skips the move, which is what free positioning is for.

The second branch is what was missing. The latch used to be called g_restored
and guarded only the restore, so FreePosition=1 with RememberGeometry=0 hit
neither branch: nothing restored it and nothing docked it, and the window sat
wherever CreateWindowExA had put it. That is a fixed screen position with no
relationship to where the client is, so on a second monitor -- or any client
not at the default spot -- it looked exactly like the window going to the wrong
place, because it was. Renaming the latch to g_positioned ("has this window
been placed yet") is most of the fix; the rest is the else.

mw_settings_refresh re-arms the latch when FreePosition or RememberGeometry
actually changes, so a toggle takes effect within a settings poll instead of at
the next restart. UnlockSize is deliberately not in that test -- it has nothing
to do with position. A consequence worth knowing: turning RememberGeometry OFF
re-docks the window, which is the honest reading of "stop remembering where I
put it" and is documented as such in defaults.ini.

Saved position is RELATIVE (WinRelX/WinRelY), size is absolute (WinW/WinH).
Every client shares one config.ini, so an absolute pair put every multi-boxed
client's chat window at the same screen coordinates, stacked; an offset from
the game window puts each beside its own client and survives the player moving
that client. WinX/WinY are the legacy absolute pair: restore_geometry uses them
verbatim once (so nothing visibly moves on the first launch after an update),
converts them against the game window, and clears them. If there is no game
window at that moment nothing is migrated and the absolute pair is kept, so the
migration simply retries next launch. The restored rect is then clamped into
the nearest monitor's work area, via MonitorFromRect -- not MonitorFromWindow,
because the question is where the window is about to be, not where it is.

ResetPosition is a one-shot COMMAND key, not a setting. Maps++ writes 1;
mw_settings_refresh clears the geometry keys, re-arms g_positioned and writes 0
back, and the next pass docks. It is a command because the ini is the only
channel there is -- there is no way to tell the DLL to do something except to
leave a note it will read within two seconds. It is deliberately absent from
_CHATMOD_SPEC on the Maps++ side, so the settings tab cannot re-issue it on
every Save.

Clearing keys is the DLL's job, always. The Maps++ side never IniDeletes
anything in [Chat]: it would race this DLL for the file, and a section rewrite
would destroy the geometry keys outright. mw_cfg_clear exists for this.

Also here: mw_cfg_str's buffer went 128 -> 256 bytes. At 128 it, not
g_tab_spec[256], was the real ceiling on the Tabs setting, and
GetPrivateProfileStringA truncates to the buffer -- so a long tab spec was cut
mid-channel and the strip came back wrong with nothing in the log to say why.


Do not
------
  - Patch main.exe on disk. If something seems to need it, re-scope.
  - Hook without a signature check. A wrong build must stand down, not crash.
  - Invent a value for anything the mirror publishes that the client also
    drives. The cursor was written as "our head" for months and silently broke
    the two scroll buttons and freeze, none of which the mod touches. Anything
    in those four counters that a vanilla control moves has to be TRANSLATED
    from the real ring, not synthesised.
  - Blanket-NOP the SetWindowPos inside the reposition function: that routine
    is also the legitimate "owner window moved" follow, and the render and
    hit-test paths read the rects it caches. The Phase 3 detour skips only the
    move and still refreshes those rects itself.
  - Use `force` as the "this is the show pass" cue in reposition_detour. It
    reads like one and is not: force=1 is set by the SNAP-BACK path as well as
    by the show path, so acting on it re-docks the window on exactly the event
    FreePosition exists to suppress. The two cannot be told apart from inside
    the detour. The g_positioned one-shot answers "has this window been placed
    yet", which is both answerable and the question that actually matters.
  - Scan a whole prologue for relative-branch opcodes. Byte scanning cannot
    tell an opcode from an operand: `mov eax,[0x7E6870]` is A1 70 68 7E 00,
    and the 0x70 in its address reads as a jcc rel8. Only the first byte is
    an opcode; the real guarantee is that the signature pins the bytes.
  - Change font size without regenerating the chip atlas (built once at window
    creation) — the text and the channel chips will disagree.
  - Compact or punch holes in the real message ring to hide a name. Drop at
    append for new messages; skip in keep_message for the chat window's
    leftovers; let overlay leftovers age out. Rewriting the real ring in
    place is the class of change that crashed the client during tab work.

---------------------------------------------
Taken from a real logged-in session, not from static analysis:

  chat HWND class "WindowedMode", title "CHAT WINDOW", style 0x14C40000
    (the 0x04C40000 from CreateWindowExA plus WS_VISIBLE added by ShowWindow)
  window rect 806,0  236x639     client 220x600
  font "Courier New" h=16 w=8 weight=400 charset=1 pitch=0x31
  WndProc live == resolved, i.e. nothing else had subclassed the window

Two corrections to the static read, both worth knowing before Phase 2 and 5:

  - The memory DC is created 760x600, but that is the maximum. The live client
    area is only 220x600. Size the tab strip and any font metrics work against
    the real client rect, not the 760 the bitmap was allocated at.
  - In a 0xC0 message record, +0x08 is the SENDER NAME, not the message body
    (World records read "Rajesh", "Agapite", ...). The channel id at +0x04 is
    confirmed correct and is all the tab filter needs, but do not assume +0x08
    is the text to display.
