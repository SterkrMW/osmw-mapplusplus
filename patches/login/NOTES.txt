osmw_login — auto-login mod
===========================

Goal: each launched client fills the stock login screen, submits credentials,
picks a roster character, and enters the world. main.exe is never modified on
disk.

Status: in-game verified 2026-08-30 (account fill, password +0x7C, submit
+0xA0, character select). Maps++ UI/launch wiring is a separate repo — see
docs/superpowers/plans/2026-08-30-mapsplusplus-autologin.md (copy that file
into the Maps++ tree). This repo is done for the DLL.

Delivery: 32-bit DLL injected at launch (same path as osmw_chat). Hook points
are pattern-scanned at runtime.

Static probe (build 0x45650696)
-------------------------------

Login is not Win32 EDIT controls. The JPEG system\c1meu008.jpg is the art;
the two boxes are derived widgets sitting on the login-loop stack.

  Account widget vtable   0x004D7278   (written at 0x40157A)
  Password widget vtable  0x004D73C8   (written at 0x4015AD, masks with '*')
  Focused widget          [0x0065EE18]
  Insert-char             vtable+0x18 = 0x0047AE20 (account glyphs)
                          __thiscall, 3 extra args (ch, 0, 0), ret 0x0C
  Password char           vtable+0x7C = 0x004023D0
                          __thiscall, 1 stack arg, ret 4. Draws '*' via
                          0x47B740 and appends the real char to the CUtlString
                          at widget+0x138 (length at +0x144). Shared +0x18 does
                          not advance password +0xD8.
  Submit                  password vtable+0xA0 = 0x00401350
                          copies account (inner +0x14C, +0x6C) and the
                          CUtlString, send4(0x00020000), Result=0. Refuses
                          empty glyphs ("Please enter the correct username
                          and password"). 0x47BFA0 sums glyph cells at +0xCC.
  Leave / back            [0x0065EE08] = 1, [0x0065EE14] = -2 (0x401D97).
                          Loop tail then send4(0x00030007) and return -2 --
                          the parent goes back to the start task. This is NOT
                          login submit.
  Login loop tick         0x00401A53   mov [0x65EE08], ebx  then call 0x45F3F0
                          0x00401A62   cmp [0x65EE08], ebx  (hook here, after
                          the input pump). Widgets exist by then.

Do not memcpy a C string into widget+0xCC — that is a 16-byte-per-glyph cell
array. Account: call +0x18. Password: call +0x7C, then +0xA0.

Shipped into the game root: osmw_login.dll, osmw_login_launch.exe
(osmw_chat_launch.exe also injects the login DLL when it is present).

Settings: TWO gates, both must pass, checked in dllmain.c's worker.

  [Addons] AutoLogin in config.ini / defaults.ini -- the persistent master
  enable, as before.

  OSMW_AUTOLOGIN in the environment -- per-launch consent. Absent, or "0",
  means no.

The second exists because the first cannot express "this launch". It is
persistent, so whatever Maps++ last wrote for its own launch was still sitting
there for a client the player started by hand afterwards: running
osmw_chat_launch.exe on its own would log itself in. It could not simply be
parked at 0 between launches either, because that same key doubles as Maps++'s
addon-enable flag for its roster editor -- one key, two meanings, which is the
actual defect. Maps++ no longer writes [Addons] AutoLogin at launch at all.

An environment variable is carried by the process tree rather than by the disk.
Maps++ sets it immediately before Run() and clears it once the batch is
spawned; both launchers already pass NULL for lpEnvironment in CreateProcess,
so main.exe inherits it through the injection chain and NEITHER LAUNCHER NEEDED
CHANGING. A client started from Explorer inherits Explorer's environment, has
no such variable, and logs in normally.

Verified both ways against a live client, 2026-08-30: with no variable the log
reads "OSMW_AUTOLOGIN not set -- this client was not launched with auto-login,
standing down, client untouched"; with it set, all 10 signatures resolve and
the claim proceeds as before.

Empty roster is a no-op. Roster: login_roster.dat beside main.exe (DPAPI,
description L"osmw_login"). Edit with osmw_login_launch.exe --roster (Win32)
or, once Maps++ hosts it, ui/login_roster/.

Logging is OFF unless asked for
-------------------------------
[Debug] ModLogging in the game root's config.ini, default 0, read once in
dllmain.c's worker beside the two gates above. Clear, and no file is opened:
every lg_log() is a no-op, including the "standing down" lines that say WHICH
gate stopped a client. That is the trade -- five clients a launch meant five
osmw_login.<pid>.log files a launch for a player who was not debugging
anything, so the answer to "why did this client not log in" is now "turn on
Tray -> Debug -> Client Mod Logging in Maps++, relaunch, and look again".

One key, shared with osmw_chat.dll, and the same shape in both: on keeps the
five newest logs and caps each at 1 MB; off prunes to zero, so switching it
back off clears what the troubleshooting session wrote. A live client's file
survives either way -- it is held without FILE_SHARE_DELETE, so the delete
fails and we move on. Keep patches/chatmod/src/log.c and this mod's log.c in
step; the reasoning is written out at length in the chatmod one.

Read at injection, so it applies to clients launched after the change, never to
ones already running.

OSMW_LOGIN_ROW -- which row, not whether
----------------------------------------
Optional, carried the same way and read beside the consent variable. Its value
is an opaque roster row id (LG_ID_MAX-1 chars at most; anything longer is
treated as absent rather than acted on as a truncated prefix, which could name
the wrong row). Absent means "next free enabled row", i.e. the behaviour that
shipped before it existed.

It exists because the claim table answers "is this row taken" but nothing ever
answered "which row should THIS client take". Five clients each grabbing the
next free row is fine until the player wants two named teams, and the order is
not even spawn order -- the clients' worker threads race each other for the
table. Maps++ sets the variable immediately before the Run() for the one client
it applies to, inside its launch loop, and clears it with OSMW_AUTOLOGIN once
the batch is spawned. Run() snapshots the environment at CreateProcess, so a
per-client value is safe there.

Two deliberate asymmetries against the next-free path:

  - A named row is claimed whether or not it is enabled. Naming it is the
    explicit act; `enabled` only governs where the next-free walk may wander.
  - A named row already held by a live PID does NOT fall back to another row.
    The client stands down at the stock login screen and, with logging on,
    says "requested row <id> unavailable -- standing down". Logging into somebody
    else's account is the worse answer, and the server rejects a duplicate
    account login regardless (see the 0x454A52 note above).

It cannot bypass consent: OSMW_AUTOLOGIN and [Addons] AutoLogin are still both
required before this is read at all.

The name is duplicated in dllmain.c (LG_ROW_VAR) and addons/auto_login.ahk
(_AUTOLOGIN_ROW_VAR) -- change both together, as with the consent variable.

Maps++ (same repo, since the move)
----------------------------------
Do not re-implement login in AHK. Maps++ keeps GamePath on main.exe and starts
osmw_chat_launch.exe beside it (ResolveLaunchExecutable), which injects
osmw_login.dll then osmw_chat.dll. Maps++ launches N clients and sets
OSMW_AUTOLOGIN for them; each process then claims a row on its own, unless
Maps++ named one per client with OSMW_LOGIN_ROW.

Sources moved into the Maps++ repo, so the DLL in Lib/ and the code that built
it now share one history and build.ps1 checks they agree. Build with
python patches/login/tools/build.py -- see patches/README.md.
